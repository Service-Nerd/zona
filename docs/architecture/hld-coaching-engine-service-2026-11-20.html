Coaching Engine Service

The coaching engine becomes one callable service with a defined contract, built as layers, where each fact has exactly one owner. We measure it against today's engine before any runner sees it, and every defect it produces is caught, recorded and turned into a regression test automatically.

Proposal: needs founder approval Run engine + strength engine Doctrine unchanged: the code changes, not the principles

1. What we are trying to achieve

Plans we are happy with

0 hard-rule violations, 0 findings in every real-defect class, every note true about its own plan.

Never worse

Nothing ships unless it beats today's engine on a fixed scorecard, on production-shaped inputs.

A callable service

One versioned contract that the app, the website and any future client call the same way.

Canonical truths

Runner profile, rules, the delivered plan and its explanations, each owned in exactly one place.

Defects caught automatically

Every plan is checked when it is generated and again each night. Every failure becomes a recorded defect and a test case.

Explainable

Every number in a plan can say which rule set it, and every note is generated from that record.

3. Target architecture: layered service

Every request passes through the same layers in the same order. Each layer owns one kind of truth and may only read the layers below it. There are no post-passes: if a layer finds a problem, it is resolved inside that layer or the request is refused with a reason.

API
Engine API (versioned contract)
POST /v1/plans · /v1/plans/{id}/adapt · /v1/checkpoint · /v1/strength. A refusal is returned as a result, not thrown. Every call states its as_of date, so the same request always gives the same plan.
L1
Profile: input normalisation
Wizard answers → one RunnerProfile: assessed vs declared level, VDOT with its date, effective starting km, capacity per day (time × pace), injuries as constraint tags, one weeks-to-race counter, explicit "age unknown".
Canonical truth: who the runner is
L2
Doctrine: the rule catalogue
Every principle is a data entry: id, §, scope, kind (hard / soft / prefer), parameter from GENERATION_CONFIG, explanation template. Session catalogue and plan signatures live here.
Canonical truth: what we believe
L3
Planner: block → week → session
Block planner composes phases (foundation, base-build, staged, build, peak, taper, race, recovery, maintenance). This replaces the separate builders. Week planner sets volume within capacity. Session placer sizes and places sessions under every rule at once, and is the single owner of delivered volume. Strength placement uses the same week and availability model.
Canonical truth: the delivered plan
L4
Explanation
Each planner decision writes a record: what it set, which rule bound it, and the runner's lever. Notes are generated from these records only, so they cannot contradict the sessions.
Canonical truth: why
L5
Verifier (independent)
It evaluates the L2 catalogue over the output with its own code, never the planner's, and adds the quality auditor and note-truth checks. A plan with an error never leaves the service.
Canonical truth: is it right
L6
Enrichment (optional AI)
Voice and coaching copy only. It cannot change a number. Its output is re-verified, and the rule output is returned unchanged if it fails (ADR-006 kept).

Stays outside the service

  • Auth and tier resolution (ADR-003)
  • Persistence, archive, supersede
  • Screens, push, weekly reports
  • Activity ingest (HealthKit SOR)
  • AI chat and coach notes

Moves into the service

  • All 12+ builders, as planner configurations
  • Strength engine (same profile and week model)
  • Validation, as the verifier
  • Note writing, as explanation

4. Benchmark: how "never worse" is proved

The golden corpus (built first)

  • Generated from the wizard's own answer space, so it matches what production sends
  • Every variant: 2–7 days, blocked weekends, caps, every injury chip and combination, age missing, every race weekday
  • Plus the live stored inputs (anonymised), the personas, and every defect fixture ever found
  • A gate refuses any corpus row the product could not produce

Scorecard v2 (one number set)

  • Hard-rule errors: must be 0
  • Each FIX objection class: count, target 0
  • Note truth: % of notes whose claim holds, target 100%
  • Fit rate (envelope), fitness build, specificity: no worse than today
  • Plan-level diff vs today: every change explained by a named rule
Rule of the build: the current engine is measured on this scorecard first. That baseline is the bar. A planner configuration replaces the old path only when it scores at least as well on every line and better on its target classes, in shadow mode, on real requests.

Automatic: detection, recording, grouping, the backlog item, the regression test case, the CI ratchet, regenerating eligible live plans, and refusing to ship an error plan.

Still a decision: changing a rule. A new failure class goes to the Coaching Board, and its fix lands in the L2 catalogue. Because rules are data with one evaluator, a rule fix applies to every plan kind at once.

7. Context: how others do it, and where we differ

Template-led apps (Runna, Nike Run Club, Garmin's race plans) pick a template and adapt paces. Daily-suggestion systems (Garmin's suggested workouts, Athletica) re-plan each day from load and readiness. Coach platforms (TrainingPeaks, Final Surge) leave the rules to a human. Zonna's position is restraint: zone discipline the runner can see and trust. That makes explainability a product requirement. The constraint-based planner with decision records (L3 + L4) is what lets every "why" be true. A service contract with explicit as_of and versioning is also what a future B2B or partner use would need.

8. Build and migration plan

Freeze: no more patches to the current engine, except a short hotfix list of defects that can harm a runner today: run-walk on a maximal time trial, base-build ramps ignoring injury caps, per-side plyo dose. Each hotfix is regression-tested. Everything else goes into the new layers.
B0

Measure first

Build the golden corpus and Scorecard v2, including today's ~46 predicates and note-truth checks. Baseline the current engine on it. Wire the verifier into production generation as observe-only, so defects start being recorded now.

Exit: baseline scorecard committed; production findings flowing; the corpus gate falsified.
B1

Contracts and canonical models

Engine API v2 (request and response, refusal as a result, as_of, version), RunnerProfile, Rule schema, strict Plan v2 with a v1 adapter so screens keep working, Decision and Finding.

Exit: contracts reviewed; v1↔v2 adapter round-trips every stored plan.
B2

L1 Profile, adopted by the current engine first

One normaliser replaces scattered assessment. This alone removes the input-layer defect classes, and it is low risk because the planner does not change.

Exit: scorecard ≥ baseline; every plan diff explained; Coaching Board on any prescription change.
B3

L2 catalogue + L5 verifier

Port config + invariants + strength codes into rules, each tracing to a §. The independent verifier replaces validatePlan as the gate. New doctrine questions are ruled here and land as rules.

Exit: the verifier finds every known defect class on the current engine (falsified class by class); 0 false positives on the golden corpus.
B4

L3 planner, one plan kind at a time (strangler)

Order: 5K/10K race → HM → marathon → foundation and base-build and get-running → staged and walk-run → maintenance and recovery → ultra → adapt/modify/recalibrate. Each runs in shadow beside the old path on real requests before cut-over.

Exit per kind: ≥ baseline on every scorecard line; target classes at 0; shadow diff explained; Coaching Board sign-off; then traffic is switched behind a flag, with rollback.
B5

L4 explanations

Notes generated from decision records. The fallback chains are retired per plan kind as it cuts over. Copy is written on the founder's delegation; Design Board for any surface change.

Exit: note truth 100% on the golden corpus.
B6

Strength on the shared model

Strength reads RunnerProfile and the week model: blocked days, day off, and the run load in the same week. The pairing, carry and dose rulings land as rules.

Exit: strength scorecard ≥ baseline; release conditions met (founder phone check).
B7

Service extraction

The engine is deployed as its own versioned service behind the contract (a package first, then a separate deployment), and the app calls it through one adapter. The 806-line route becomes a thin caller.

Exit: app, website and scripts all call the API; there are no direct engine imports (gated).
B8

Live-plan migration

Regenerate plans for runners with no logged runs (founder 2026-11-20). Others keep their plan under the v1 adapter, verified nightly. Retire the old engine once no traffic and no stored plan needs it.

Exit: old engine deleted; nightly verifier green; defect register empty or ruled.

9b. Improvements to the design

Areav1 gapv1.1
Verifier independence"Independent code" was ambiguous. If the planner and verifier compute weekly km differently, we get false findings; if they share a buggy derivation, we get blind spots (the plyo case).Two kinds of shared code are allowed: the rule data and the metrics owner, which is tested against hand-computed fixtures. Predicates are never shared with construction logic, and the planner never calls a predicate to make a plan look valid.
VersioningVersion was mentioned without saying what is versionedEvery plan is stamped with engine_version, rules_version (a catalogue hash), as_of and input_hash. The nightly verifier separates "defect at creation" from "rule changed since", so a doctrine change never reads as a regression.
Latency and AIThe generate path takes 28–35 s todayThe rule plan returns synchronously. Enrichment is a separate async job, called by the route (ADR-006 unchanged, persistence stays outside the engine). Shadow runs execute after the response, in waitUntil, so they add no latency for the runner.
Error modelRefusal-as-result named, taxonomy notA typed result: ok / refused {code, reason, levers[]} / invalid_input {field, why}. A 422 maps to refused, a 400 to invalid input, and a 500 is reserved for engine faults (which also emit a finding). The four current refusal names map to codes.
ConsumersScreens read raw meta keys (118, 8 cast-only)A plan read model: typed accessors are the only way screens, prompts and push read a plan, so v1 and v2 plans differ in one place. This extends the loadResidualNote pattern.
Planner complexity"Constraint solver" could become over-engineering (the Sensible principle)Deterministic, priority-ordered placement: a fixed order of hard rules, then soft rules, then preferences, each stage working within the room the earlier stages left. No external solver library. When a rule cannot be met, it is recorded as a Decision with its lever rather than silently relaxed.
AdaptationNot specified in v1/adapt returns a proposed plan plus a diff and its ADR-012 magnitude. The app decides whether to auto-apply or confirm. ADR-012 and ADR-013 are unchanged.
Flags and rollbackCut-over "behind a flag"One flag per plan kind, readable at runtime, plus a global kill switch back to v1 and a shadow-diff dashboard. Each cut-over is an explicit, recorded founder or Coaching Board sign-off.
Governance hooksThe new rule catalogue would bypass coaching-guardThe catalogue file joins the doctrine file list (INV-COACH-001). The three-artifacts rule (INV-COACH-002) becomes: § + config key + rule entry with predicate.
Doc driftThe inventory found stale docsPart of B1. architecture.md still says Gist, AI generator and dark mode. The principles skill itself still says Gist, theme toggle and red intervals. The engine and strength contracts carry stale counts. CLAUDE.md has 4 stale claims. Fixed in the same commit as the contract (D-11, GOV-001).
TierNot explicitThe engine stays tier-blind: measured 0 of 300 differences today. Tier is resolved at the route (ADR-003). Paid richness belongs to L6 and the app, never to the prescription.
Save pathThe background chain writes plan_json with a direct update, bypassing savePlanForUserHotfix list: every plan write goes through the one save owner (D-08, N-015).
